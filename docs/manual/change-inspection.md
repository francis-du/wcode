# Read-only code changes

In the next-version implementation, open **Current changes** and select a file path. The existing workspace opens an inline read-only unified diff, not an editor. Compare **HEAD → working tree**, **HEAD → index (staged)**, or **Index → working tree**. The left gutter is the original line, and the right gutter is the resulting line. Added and removed lines retain their signs as well as theme colors.

A file snapshot records HEAD, selected index identity and current file SHA before and after inspection. Switching layers pins that captured snapshot; if it changes, the response contains no patch and asks you to reload. A snapshot is a bounded observation, not a transaction or continuous live proof. Project refresh, failed refresh, restored cache and workspace switches invalidate the view. Raw code is not added to the project snapshot cache or local storage.

Untracked files show an explicitly labeled source preview, not a fabricated committed baseline. Empty output means only the selected comparison layer has no differences. Binary/unavailable, redacted and truncated results do not imply complete code coverage. Patches are limited to 64 KiB, untracked source uses the existing 1,000-line read window, and the browser renders at most 1,500 rows. The server also returns bounded typed before/after changed-line ranges from the changed rows it actually returned, not from surrounding hunk context; adjacent changed rows are merged and partial range coverage stays explicit. The browser preserves those coordinates as typed JSON integers across change ranges, mapped symbol start/end lines and impact relation line/character fields; numeric strings or other coercible values are rejected instead of becoming source-navigation coordinates. Those coordinates now feed bounded before/after Tree-sitter mapping. For tracked paths with a baseline at the same path, the exact captured HEAD source (working/staged) or index source (unstaged) is parsed separately and only returned before-line ranges are mapped to baseline definitions. The after side is mapped against its own exact source identity; staged after-state uses the captured index blob instead of newer unstaged worktree bytes, while worktree mapping still requires the captured worktree SHA. The two sides are shown separately, capped at 128 symbols each, suppressed for redacted source, and marked partial when change or outline coverage is bounded. A structurally incomplete outline or a declared definition with a missing/invalid range or Tree-sitter syntax identity is also treated as partial coverage; WCode drops that unusable row instead of making the remaining definitions look complete. Pure addition- or deletion-only body edits can otherwise make a surviving function appear on only one side, so the exact opposite snapshot may add a display-only counterpart only when Tree-sitter finds exactly one definition with the same non-empty qualified name and kind. Each mapped symbol carries a required boolean `counterpart_only`; malformed or missing metadata is rejected by the browser. The browser does not trust that flag by itself: each symbol's `changed_ranges` must exactly equal the intersections of its Tree-sitter line range with the captured changed-line ranges for the same side. Direct rows require at least one exact intersection; paired counterparts require none and must carry an empty range list. A mismatch fails closed instead of promoting a file change into a function-body change. A `true` row is visibly labeled **Paired counterpart · no changed-line overlap**, carries no changed-line ranges, and ambiguous or missing matches stay absent. Counterpart-only after rows stay display-only: they cannot open Code Graph or request impact as though they were directly changed definitions. Directly overlapped before/after definitions with returned changed ranges also expose **Reveal changed line**, which stays inside the same captured diff and jumps to that side's visible changed row only after revalidating the current path, snapshot, side/node membership and range containment. Counterpart-only rows intentionally have no such action; this is local patch navigation, not historical-source retrieval or semantic proof. For one unique same-qualified-name + kind pair, the inspector can also report whether the exact non-redacted Tree-sitter signature text changed or stayed the same. When both exact syntax outlines are complete, the same identity check also labels an overlapped definition as modified when one opposite-side identity exists, or as path-local added/removed when none exists; ambiguous identities stay unknown. These are syntax-only observations, not a semantic signature, API-compatibility judgment, semantic impact or rename proof. Exact staged/index symbols whose bytes differ from the current worktree are also display-only rather than clickable into the current-worktree Code Graph. Rename detection remains disabled: this slice preserves literal path-local add/delete rather than promising cross-file rename pairing.

Inspection reuses Workspace protected-path/symlink checks and fixed policy-checked Git commands. An initialized HEAD and accessible parent directory are currently required. Deleted directory trees, unmerged index entries, submodules, unrestricted commit ranges and full historical source browsing are not supported by this first slice. A path or repository-state failure is explicit, not a claim that the tree is clean. The endpoint does not accept shell commands, arbitrary revision expressions, write requests or approvals.

Code Graph now adds the next narrow navigation step: a selected stored graph node can open a read-only source window derived from that node's own path and line range. When navigation starts from a changed worktree symbol, the browser first verifies that the requested Tree-sitter node still belongs to the current change-detail mapping for the same snapshot and worktree SHA with `source_state=worktree`; staged, stale or non-mapped syntax nodes are rejected before navigation. That focus request then carries the exact code + Design revision captured by change-detail. The server checks it before graph construction, rebuilds the current graph for that matching repository state, and checks the repository revision again afterwards; mismatch or concurrent drift returns a stale-change conflict rather than silently navigating into newer code. The browser sends only the node id and graph snapshot id; the server resolves the path from the stored graph, reads through the protected Workspace boundary, and returns source only when its SHA still matches the node's captured source identity. A mismatch is a stale-source conflict rather than a silent jump to newer bytes. The window is bounded to 240 lines, keeps redaction/truncation visible, and keeps rendered line numbers inside the server-returned range even when the file ends with a newline. If the response's declared line interval, focus range or source row count disagree, the browser rejects the payload instead of silently rendering an incomplete window. It never upgrades Tree-sitter syntax relations into semantic proof.

For an after-state definition backed by the exact current worktree bytes, **Explain impact** performs a second snapshot-bound check before asking semantic navigation about that changed symbol. Before any impact request is sent, the browser requires the symbol mapping path and snapshot id to still match the rendered change-detail view, requires the mapping source SHA to equal the captured worktree SHA, and requires the selected node to remain a directly overlapped after symbol. The server repeats this boundary after remapping the exact snapshot: even a matching Tree-sitter node id cannot enter semantic navigation unless that remapped after-symbol is explicitly direct (`counterpart_only=false`). Changed-symbol graph, impact and degraded syntax-caller actions re-run the complete symbol-mapping validation at action time, including exact changed-range intersections, so stale or later-mutated in-memory mapping cannot become function-level navigation; invalid mappings fail closed without a request or graph jump. When an impact request finishes, the browser performs the direct-symbol mapping check again against the still-current change-detail path, snapshot and worktree bytes before accepting any relations; a mapping that changed while the request was in flight cannot attach callers, references or implementations to a symbol that no longer qualifies as directly changed. The request also carries the exact repository code + Design revision captured by change-detail; a different starting revision is rejected, and the server rechecks that whole-repository revision after cross-file semantic/search work before returning relations. With a live language server, the result can include semantic incoming calls, references and implementations. If the language server is unavailable, the panel says so and falls back to bounded Tree-sitter incoming-call candidates plus a separate bounded set of exact text matches; it does not fabricate semantic references or implementations. Text matches carry the SHA of the scanned source and a bounded excerpt, but they are only mentions—not callers, references, semantic proof or Verification Evidence. When a degraded Tree-sitter caller retains a concrete syntax graph node id, that caller is clickable into the same captured-revision Code Graph and then its protected read-only source preview only while the caller node is still present in the accepted incoming-call result for the same selected symbol and snapshot; navigation checks that relation result instead of the changed file's own symbol list; the browser labels this action `Open in Code Graph · syntax node`, while semantic-only relation rows stay display-only. The node id is navigation provenance, not semantic authority. Live semantic incoming/reference/implementation rows do not carry Tree-sitter graph node ids: server normalization rejects semantic-navigation output that mixes in that syntax identity, and the browser independently rejects semantic payloads that try to mix it back in. Each relationship/search class is capped at 24 results. If a relation/search row is malformed or the relation cap is reached, the server drops the unusable row but forces the result to remain visibly partial instead of presenting the surviving subset as complete. A present incoming-call, reference, implementation or exact-search collection with a non-array shape is also malformed and forces partial coverage instead of being interpreted as an empty complete class. Semantic impact also remains partial when a required semantic relation collection is absent, when raw `queried` coverage does not contain exactly the Impact query classes `references`, `implementations` and `calls`, or when the live provider omits or malforms the required `unsupported`/`failures` outcome arrays or reports any unsupported or failed Impact subquery; an empty semantic relation array is complete only when that query is explicitly covered and both outcome arrays are present and confirm that it did not fail or declare unsupported. If a provider advertises call-hierarchy support, `prepareCallHierarchy` must return exactly one structurally valid item before WCode treats `calls` as queryable. Zero items or multiple prepared candidates are failed/ambiguous `calls` coverage; WCode does not arbitrarily choose the first target. The unique item must contain the required name, kind, URI, range and selectionRange shape before WCode queries it; both ranges must include ordered integer start/end line and character coordinates with start less than or equal to end, and selectionRange must stay fully inside range. WCode also binds that prepared item to the exact request before sending any call-hierarchy query: the URI must equal the requested document, selectionRange must contain the original LSP position under LSP half-open range semantics (`start <= position < end`), so a query exactly at the exclusive end is outside the symbol, and both range endpoints must decode exactly inside that source with the negotiated position encoding. A structurally valid item for another document/symbol, or one with out-of-source coordinates, is failed `calls` coverage rather than evidence of no callers. Empty, incomplete, reversed or out-of-range selection ranges are malformed, so an absent or malformed prepared item keeps an empty incoming-call array partial instead of presenting complete evidence of no callers. Relation locations from the language server must also carry valid ordered range structure for the target source. Every present `selectionRange`, `range`, `targetSelectionRange` or `targetRange` must have integer start/end coordinates with start no later than end, and both endpoints are decoded strictly in the negotiated position encoding. Direct Location and LocationLink wire identities are not interchangeable: exactly one of `uri` or `targetUri` may identify the row. A target-link row must carry both `targetRange` and `targetSelectionRange`, with the selection fully contained by the target range; a direct `uri` row cannot also carry target-range fields. Mixed or contradictory identity is discarded and keeps relation coverage incomplete. Call-hierarchy relation entries are stricter: each returned `from`/`to` item must include a complete CallHierarchyItem name, kind, URI, range and selectionRange, with selectionRange fully contained by range; malformed items are discarded and keep coverage incomplete. Every relation must also include a non-empty `fromRanges` array; each call-site range must be ordered, stay inside the actual caller symbol range (the returned `from` item for incoming calls, the prepared source item for outgoing calls), and decode exactly inside that caller source with the negotiated position encoding. Missing, malformed, out-of-caller or out-of-source call-site ranges discard the relation and keep coverage incomplete. Position decoding remains strict: UTF-8 offsets cannot split a code point or run past the logical line, UTF-16 offsets cannot split a code point or run past the logical line, and UTF-32 character indices cannot run past the logical line. With CRLF source, the trailing carriage return belongs to the line ending and is not an addressable LSP character; offsets that target it are rejected. Invalid or out-of-source ranges are dropped and keep coverage incomplete rather than being clamped, rounded or partially trusted. On degraded fallback, unavailable or malformed `syntax_calls.incoming_calls`, or unavailable/non-array `keyword_matches`, also keep the result partial because a missing fallback class is not a complete empty impact. Truncation and redaction metadata are typed too: a present non-boolean truncation flag keeps coverage partial, and an exact-search row with malformed `redacted` metadata is withheld and marks the result partial rather than being exposed as ordinary source text. Degraded exact-search rows with an empty path, a non-positive line, or an invalid scanned-source SHA are treated as malformed rather than disappearing silently. A degraded syntax caller with a present but invalid Tree-sitter `node_id` also makes coverage partial when that unusable navigation identity is discarded; relation line and character coordinates are 1-based integers, and zero or coercible string coordinates fail closed in the browser. Partial coverage remains partial relations, not “evidence.” The panel names the selected changed symbol and keeps incoming callers, references, implementations and exact search matches visually separate so their meanings are not collapsed. The server validates raw semantic-navigation provenance before publishing impact data: a present `degraded` field must be boolean rather than being silently treated as semantic mode; the runtime fallback route `degraded_syntax_and_keyword_search` is accepted only with matching syntax provenance and is canonically exposed as `routing=syntax-degraded`; degraded payloads carrying semantic references or implementations fail closed instead of being silently discarded. The server accepts the runtime's raw semantic route only as `cross_file_semantic` and canonicalizes it to public/browser `routing=lsp`; raw `lsp` is not accepted as runtime provenance. The raw semantic-navigation path must also be present and exactly match the selected changed path, so relations produced for another file cannot be relabeled onto this change. The returned semantic-navigation selector is then checked against the selected changed definition: its source revision must match the captured worktree SHA, its resolved start line must match the changed symbol's selected line, and its resolved name must exactly match the selected changed-symbol selector. For live semantic output, the provider query line and character must also be present and exactly match that selector position. A response from another path, queried or resolved at another position, or resolved to another name is rejected instead of being relabeled as impact for the requested symbol. The browser rejects contradictory precision metadata: syntax fallback is accepted only with `provider=tree-sitter+search`, `routing=syntax-degraded`, `degraded_from=lsp` and cannot carry semantic references or implementations; semantic results require `routing=lsp` and the runtime LSP provider identity `provider=lsp:<provider-id>`; arbitrary non-LSP provider names and the reserved syntax fallback provider `tree-sitter+search` are rejected, and semantic results cannot also claim degradation, degraded search matches, or Tree-sitter node ids. Live semantic output is labeled as relationships, not Verification Evidence. Exact staged/index symbols whose bytes differ from the worktree cannot use this current-worktree impact action.

Collection-valued LSP navigation responses stay protocol-shaped. References accept only an array or `null`; definition and implementation may additionally normalize one singleton direct `Location`. At this boundary an ordinary direct `Location` is exactly the `uri` + `range` wire shape: an object that also carries `selectionRange` is not accepted as a Location, while CallHierarchyItem keeps its separately validated `selectionRange`. A singleton object in a collection-only response, or a singleton `LocationLink` where the protocol requires a link array, is rejected and keeps semantic coverage incomplete rather than publishing a fabricated relation.

The inspector now also captures the authoritative whole-repository code + Design revision around the file/symbol read. If that repository revision changes before the response completes, the request fails closed instead of combining a file snapshot with evidence from different bytes. The inline verification panel shows project-level effective Verification Evidence only when the currently loaded proof has the exact same captured code + Design revision; mismatched or historical passes and mapped tests are withheld rather than presented as current proof. The browser also fail-closes on internally contradictory proof payloads: effective result counts must add up to the declared total, returned item count/truncation must match the bounded 24-item contract, current evidence result counts must reconcile, verification ready + blocked must equal the current plan total, acceptance total/mapped/executed/passed/fresh must be non-negative integer counts with mapped and executed no greater than total and passed/fresh no greater than executed, and evidence item results must use known result states. Valid proof also shows the acceptance mapped/executed/passed/current-revision counts; “current-revision” means freshness for the captured revision, not an additional pass verdict. The Project Observatory and its RiskStatus now carry the exact code + Design revision used to build them, and the Observatory rechecks that repository revision before the snapshot is cached or returned. The inspector shows bounded project risk only when the captured change revision, Project Observatory revision, proof revision and RiskStatus revision all match exactly. Repository drift during Observatory or standalone risk assessment fails closed; stale project/proof/risk revisions withhold the risk. Structured risk rows and bug candidates remain contextual, with heuristic candidates explicitly labeled rather than promoted to Verification Evidence. Evidence counts, plan readiness and risk context are still project-level and do not prove that one selected function is correct or incorrect.

This feature is a step toward reviewing changes without an IDE. Rename pairing and symbol-specific verification attribution remain separate work; viewing a diff, syntax/semantic impact relations or source/caller graph is not evidence that the change is correct or fully tested.
