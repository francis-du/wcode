# wcode v0.8.5

v0.8.5 connects actual code changes, source navigation, impact, and revision-matched proof in the Observatory. It also improves code-to-test context, exposes measured Engineering Fitness, and fixes interaction and verification-history edge cases.

## Code and change inspection

- Inspect staged, unstaged, combined, untracked, and deleted changes through bounded read-only source and diff views.
- Bind source, diff, and impact responses to the selected Workspace, snapshot, and source SHA. Concurrent edits, stale replies, redacted content, and contradictory mappings remain explicit unavailable or partial states.
- Drill down from components to files and symbols. Semantic relations require valid provider locations, position encodings, ranges, and response shapes; textual candidates are never presented as semantic call edges.
- Show matching verification evidence beside the change. Inconsistent result counts, plan totals, states, or revisions suppress current-proof and matched-risk claims.

See [Change Inspection](../../change-inspection/) for the behavior and precision contract.

## Context retrieval and Fitness

- Rank relevant code-to-test candidates without seeding unrelated tests into the result. Macro and naming matches retain explicit textual provenance and source validation.
- Keep bounded representative matches per file and target so a frequently mentioned file cannot consume the entire search allowance. Public search ordering and pagination remain unchanged.
- Recognize JSX/TSX test and spec paths, retain up to eight exact test targets, and expose partial coverage when supplemental scanning reaches its bound.
- Show benchmark observations separately from runtime outcomes, with raw denominators, p50/p95, revision identity, and missing, partial, or historical states.
- Fitness measurements use bounded synthetic retrieval cases and selected runtime milestones. They do not establish model patch success, hidden-holdout performance, or overall release readiness.

## Verification and interaction reliability

- Find the latest matching verification plan in durable history, including histories longer than the display window.
- Rebind an Execution after its verification floor increases, preserve an already sufficient plan, and stay blocked when no sufficient proof exists.
- Restore command-palette startup and incremental retry after refresh failure.
- Isolate input-method composition, Escape, repeated shortcuts, Tab navigation, and focus restoration. Hidden project-search results cannot activate or reopen during background refresh.
- Keep accessibility selection state aligned with refreshed results; delayed access-panel focus cannot steal focus from a closed panel or the command palette.
- Synchronize English and Chinese guidance, interface copy, minimum caption sizing, and terminal brand colors.

## Compatibility and command discovery

Start coding work with `agent_context`; command timeouts retain `timed_out` and `output_incomplete` diagnostics instead of claiming success. The `balanced`, `fast`, and `light` presets keep their existing boundaries. Use `--read-only --no-exec --no-semantic` for passive inspection.

Use `wcode help-all`, `wcode help-all setup`, or `wcode help-all --json` to discover commands without starting the runtime. Development and CI use Node 24 for behavior checks, `cargo test --locked` for the complete suite, and `cargo clippy --locked --all-targets -- -D warnings` for lint validation.

## Verification and distribution

The release gate covers formatting, locked dependency checks, the complete Rust and JavaScript behavior suites, strict Clippy, release builds, Design/Traceability, bilingual documentation, and package-version consistency. Native WebKit coverage includes 240 scenarios across languages, themes, views, and screen widths. The clean-worktree 300-round adversarial workflow runs against the exact release-preparation commit before tagging.

Tag publication produces Linux x86_64, Windows x86_64, and macOS Apple Silicon, Intel, and Universal archives with SHA256 checksums. Packaged binaries must pass version/help smoke tests; macOS packages are signed and checked after final packaging, and the installer stages and verifies the binary before replacement.
