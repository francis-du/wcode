# wcode v0.5.0

v0.5.0 是一次 Semantic Runtime 里程碑。第一方 LSP 不再只是“启动 Language Server → 做一轮有界索引 → 退出”的偶发 Refresh 能力；满足 Hardened Profile 的 Provider 现在可以在 Workspace 范围内保持有界 **warm session**，Coding Agent 也获得了专门的 `semantic_navigation`，用来处理纯文本搜索和 Syntax Index 不够完整的跨文件关系问题。

这次重点不是“让 Agent 多发 LSP 请求”。默认 Coding Path 反而变得更 Task-adaptive：Tree-sitter 与 Repository Search 继续承担低成本定位，只有 Reference、Implementation、Caller、Callee、需要语义解析的 Definition/Hover 或跨文件 Impact 真正需要更强 Completeness 时，才进入 Warm Semantic Session。

## Warm Semantic Runtime

- 满足 Hardened Profile 的第一方 Semantic 默认开启；v0.5.0 首个 Automatic Provider 是 `rust-analyzer`。
- Harness 持有有界 **warm session** Pool，以 Workspace、Provider Identity、Provider Binary Identity 作为 Key。
- 后台 Semantic Graph Maintenance 与前台 `semantic_navigation` 复用同一个活跃 Provider Session，不再分别启动两份 Language Server。
- 每个 Slot 内串行化一条 JSON-RPC Protocol Stream，并保持真实的 Capacity / Idle 上限：Idle Prune 只回收未被 Lease 的 Slot；Capacity Eviction 不会删除 Active Lease；全部 Slot Busy 时直接 Fail Closed；Provider Binary 更换遇到旧 Slot 仍在使用时，也会等当前 Lease 结束后再重建。
- Document State 按 Source Revision 且按 Server Contract 同步：wcode 遵守 Server 声明的 `textDocumentSync` Full / Incremental / None；`didChange` 只按 Server 支持的形态发送；Incremental Replacement Range 使用协商出的 Position Encoding 计算；只有 Server 要求时才发送 Open/Close Notification。
- Automatic Worker 只运行在最具体的 Discovered Project Workspace，使用短暂 Stable-source Window、有界 Retry，并与 Model-facing Work 共用 Global Harness Concurrency Boundary。
- Semantic Graph Fact 继续携带 Source Revision Provenance；Stale Fact 在重新获得 Fresh Provider Evidence 前不会参与 Graph Overlay、Impact、Reconciliation 或 Context。

## 22-language LSP Conformance

v0.5.0 也重新收紧了“支持一种语言”的定义。当前 22 种 Syntax-indexed Language 每一种都必须恰好拥有一个经过 Deterministic Compatibility Test 的 Canonical LSP Launch Profile；每个 Canonical Profile 还会真实 Spawn 一个 stdio Mock LSP，并完成 wcode 的 `initialize` Framing/Capability Handshake。Provider-specific Command 与 Workspace Argument 都是正式契约，不再只是 Registry 里的一串候选名字。

- Bash 使用 `bash-language-server start`；C/C++ 使用 `clangd`；C# 使用 `csharp-ls`；CSS/HTML 通过 `--stdio` 使用 VS Code Language Server。
- Dart 使用 `dart language-server --protocol=lsp`，并携带 wcode Client Identity；Go 显式使用 `gopls serve`。
- Elixir 识别 ElixirLS `language_server.sh` / Windows Wrapper，以及常见发行版 `elixir-ls` Wrapper。
- Java 启动 `jdtls` 时分配 Workspace/Runtime 唯一的用户级 `-data` 目录，避免并行项目 Session 共享 JDT LS State。
- JavaScript/TypeScript/TSX 使用 `typescript-language-server --stdio`；Lua 使用 `lua-language-server`，同时针对 LuaLS 相对 Resource Discovery 处理 Symlink Launch。
- OCaml/Interface 使用 `ocamllsp`；PHP 使用 `phpactor language-server`；Python 使用 `pyright-langserver --stdio`；R 使用 `R --no-echo -e languageserver::run()`；Ruby 使用 `ruby-lsp`；Rust 使用 `rust-analyzer`；Swift 使用 `sourcekit-lsp`。
- 旧 OmniSharp `-lsp` 不再被算作可靠 C# Fallback。只有确实有价值的 Alternate 被保留：PHP 的 Intelephense、Python 的 pylsp、Ruby 的 Solargraph。
- 前台 `semantic_navigation` 与手工 Semantic Refresh 都会在 Canonical Provider 已存在但 Live Initialize 失败时尝试已安装 Alternate。Alternate 仍使用自己独立的 Provider/Binary Trust；Refresh 成功切换后会在 `fallbacks` 中显式报告。

Compatibility 不等于 Installation。22-profile Deterministic Handshake 证明的是 wcode 自己的 Adapter/Transport Contract；wcode 不会捆绑 22 个外部 Language Server，也不会把 Missing Executable 冒充 Semantic Support。Provider Status 现在把状态迁移做成机器可读字段：`available` 只表示存在 Executable Candidate；`launch_ready` 表示 Execution/Policy/Trust 已允许启动；`session_validated` 表示这一份 Provider Binary 已真实完成 LSP Initialize；只有随后 `runnable=true` 才进入 Semantic Precision。只有完成这层验证，并对当前 Source Revision 回答以后，结果才会成为 Semantic Evidence；否则 Runtime 明确暴露 unavailable/pending/failure，并保留 Syntax Fallback。

## Agent-native Semantic Navigation

`semantic_navigation` 面向 Agent 设计，而不是把原始 LSP Offset 直接暴露成主接口。

- 优先使用 `path + symbol`。wcode 先用 Tree-sitter Index 解析 Symbol，再把 1-based UTF-8 Byte Position 转成 Language Server 协商出的 Position Encoding。
- 已经掌握精确源码位置的调用方仍可直接使用 `line + character`。
- Intent 覆盖需要语义解析的 Definition/Hover、Reference、Implementation、Incoming Call、Outgoing Call、组合 Call Relationship 与有界 Impact Bundle。
- UTF-8 / UTF-16 Position Conversion 有显式实现和测试，Agent 不需要自己猜 Language Server Character Offset。
- Result 有数量上限、会去重，并在返回模型前重新经过 Canonical Workspace Boundary 过滤。
- `unsupported` 与 `failures` 分开：受支持的请求成功执行但没有关系时才返回空 List；LSP Error / Timeout 会作为 Failure 单独暴露，绝不会被当成“没有关系”的 Negative Semantic Evidence。
- 没有可信 Semantic Provider 可运行时，wcode 明确返回 Syntax Fallback，不会把 Tree-sitter Fact 冒充 Semantic Precision。

默认路由是有意不对称的：

```text
定位 Symbol / File
  → find_symbol / search_code / Tree-sitter

需要跨文件关系 Completeness
  → semantic_navigation
  → 复用 Warm LSP Session
```

这样普通任务保持便宜，真正依赖语义关系的任务才支付 LSP 成本。

## Safety 与 Trust Boundary

默认开启 Semantic 并不等于默认信任所有 Language Server。

- 只有拥有内置 Hardened Automatic Profile 的 Provider 才能进入默认 Semantic Lane；v0.5.0 当前只有 `rust-analyzer`。
- Provider Executable 必须解析到 Workspace 之外；Repository-local Language Server Binary 会被拒绝。
- Provider 启动前会清理敏感 Credential 与 Execution-injection Environment Variable。
- `rust-analyzer` Initialization Profile 会关闭 Build Script、Proc Macro、Cargo Auto Reload 与 Check-on-save，缩小 Repository-controlled Code Execution Surface。
- Warm Session Pool 仍然有界，而且即使 Provider 已获信任，Result-side Workspace Filtering 也不能绕过。
- `--no-semantic` 可以关闭全部第一方 Language Server Execution，并保留 Syntax Fallback。
- 没有 Automatic Profile 的 Provider 仍属于显式 Trust Expansion，需要 Provider-session `RiskyExecution` 批准；操作者也可以明确使用 Process-wide `--allow-risky-exec`。
- Provider-session Authorization 绑定 Workspace + Provider + 当前 Provider Binary Identity；Refresh/Navigation 只能复用这一份已批准的 Warm Provider，Executable 被替换后旧 Grant 自动失效。

这些措施会缩小默认执行面，但不是 OS Sandbox。Language Server 仍可能解析 Repository Metadata / Configuration，因此未 Hardened 的 Provider 不会自动运行。

## Task-adaptive Routing 与 Observability

v0.5.0 也改变了何时推荐 Semantic Work，以及 Operator 怎么判断 Warm Runtime 是否真的带来收益。

- `agent_context` 会识别 Reference、Caller、Implementation、Rename Impact、Cross-file Semantic Impact 等 Relationship-oriented Task，只有更强关系证据有价值时才推荐 `semantic_navigation`。
- 普通“这个 Symbol 在哪里”继续走 Tree-sitter/Search，不承担 LSP Startup / Query Cost。
- TUI Intelligence 会显示 Warm Session 数、已同步 Document 数、Provider Start 次数、Semantic Query 数以及 Fresh/Stale Provider State。
- Live Dashboard 进入 Alternate Screen 后会独占 Terminal Output。Tunnel/Provider Retry、Dependency Check、Reconnect、Setup Browser Diagnostic 等后台 Operator Message 全部先进入 `TaskMonitor`，不再直接写 stdout/stderr；Provider Installer 也改为捕获输出而不是继承终端，避免隧道日志漂在 ratatui 画面上把 TUI 打花。
- Graph Input 未变化时可以跳过 Graph Reconstruction，同时仍保持 Provider Session Warm，让后续 Semantic Request 不必再次支付 Process Startup Cost。
- Call Hierarchy / Implementation 只扩展高价值 Symbol，并继续保持有界，不会为每个 Variable / Field 发大量请求。
- `semantic_provider_refresh` 继续保留为 Force-refresh Surface；Hardened Lane 默认由 Runtime 自动维护。

## Compatibility 与 Upgrade

v0.5.0 不需要迁移 Workspace 或 Design State。

通过正常 Installer 安装当前 Release：

```bash
curl -fsSL https://raw.githubusercontent.com/francis-du/wcode/main/install.sh | sh
```

正在运行的 v0.4.x Process 必须重启，才能加载 v0.5.0 的 Tool Schema、Warm-session Runtime 与默认 Semantic Policy：

```bash
wcode restart
```

现有本地 `mcp-stdio` 配置与远程 `/mcp` OAuth Connection 保持原 Transport Contract。希望维持 Syntax-only Execution Posture 的 Operator 可以使用 `--no-semantic`。

Portable Agent Plugin Manifest 与 Marketplace 现在跟随 Crate Version；Release Preparation 会在 Unit Test 中同时校验 Plugin Manifest 与两个 Marketplace 的 Version 是否等于 `CARGO_PKG_VERSION`，Tag Workflow 还会独立再检查一次同一组 Release Metadata。

## Release Gate

v0.5.0 是 Milestone Release，只应对真正通过完整 Pipeline 的 Tagged Revision 做发布声明。

本地 Release Preparation 要求：

```text
git diff --check
cargo check --locked
cargo fmt --check
cargo test --locked
cargo clippy --locked -- -D warnings
cargo build --release --locked
```

Repository Governance 同样必须保持 Green：Design State 有效；Requirement → Component、Design → Implementation、Acceptance → Verification Traceability 完整；Required Convention 没有失败；Product Scope Mapping 完整；中英文 Documentation Parity 保持一致。

GitHub Release Workflow 还会独立运行 Governance Check、All-target Clippy、Installer Syntax Validation、Linux/macOS/Windows Test、平台 Optimized Build、Binary Version Check、Archive Generation 与 SHA-256 Checksum，全部通过后才发布 Release Asset。Local Green Evidence 只是发布准备；最终 Release Evidence 来自 Published Tag 与 CI Artifact。
