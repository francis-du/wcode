# wcode v0.9.1

**Maintenance release published on 2026-10-23.** This release improves task activity, fixes discovery of independent Cargo projects, and maintains TLS and macOS dependencies. Command authorization and protected-path boundaries are unchanged. WTeam payments, enterprise identity and databases are not deployed with this release.

[Release and downloads](https://github.com/francis-du/wcode/releases/tag/v0.9.1) · [Full code comparison](https://github.com/francis-du/wcode/compare/v0.9.0...v0.9.1) · [First installation](../../getting-started/) · [CLI and MCP reference](../../reference/)

## Changes and their practical effects

| Change | What it means for users |
| --- | --- |
| Status and UI/MCP-origin filters for retained jobs | Find records already returned by the server, with matching and retained counts. This is not a complete process history. |
| Workspace-, session- and task-bound refresh and cancellation | After selecting task B, a callback left over from task A cannot cancel B. Late replies and queued polls cannot replace the new selection. |
| Independent nested Cargo workspace discovery | Both explicit `[workspace]` and top-level inline `workspace = {}` tables preserve an independent verification scope. Ordinary members remain covered by their owning workspace. |
| TLS patches and macOS dependency pruning | Update locked TLS verification dependencies and disable unused X11/Wayland default features while retaining native window-handle support. |
| Cross-platform regression isolation | Sandbox tests initialize private state roots in fresh child processes instead of depending on another test's execution order. Missing protected roots still fail closed in production. |

## Upgrade an existing installation, then reconnect

Save your work and inspect any tasks whose state you need to preserve before running:

```bash
wcode --version
wcode update
wcode --version
```

`wcode update` uses the current installation location and fetches the latest stable release available when it runs. **It is not a pinned-version selector.** For exactly v0.9.1, use the fixed release downloads above and verify checksums. Do not add an unsupported `wcode update --version ...` argument.

After the update completes, reconnect your local MCP Host so it starts a new `wcode mcp-stdio` process. Existing stdio sessions continue running the old process; replacing a file on disk does not upgrade a live session. A standalone TUI/HTTP service also needs an operator-controlled restart after inspecting active work. The installer does not migrate running tasks for you.

On Windows, the update helper replaces the executable after the current update process exits. A message saying the update is ready is not completion. Check the version after that helper finishes. A newly launched command should report `wcode 0.9.1`; this alone does not prove an older service has restarted.

When versions differ, use `command -v wcode` on Unix or `Get-Command wcode` in PowerShell to identify the executable, then compare it with the path configured in your Host. Do not delete authority state or broadly grant directory access to resolve a version mismatch.

## Manual downloads and integrity checks

| Platform | Archive |
| --- | --- |
| Linux x86_64 | `wcode-linux-x86_64.tar.gz` |
| macOS Apple Silicon | `wcode-macos-aarch64.tar.gz` |
| macOS Intel | `wcode-macos-x86_64.tar.gz` |
| macOS universal | `wcode-macos-universal.tar.gz` |
| Windows x86_64 | `wcode-windows-x86_64.zip` |

Download the archive and `SHA256SUMS` from the same v0.9.1 release. Compute SHA-256 and compare the entire value with the entry for that exact filename:

```bash
# Linux
sha256sum wcode-linux-x86_64.tar.gz
# macOS Apple Silicon
shasum -a 256 wcode-macos-aarch64.tar.gz
```

```powershell
Get-FileHash .\wcode-windows-x86_64.zip -Algorithm SHA256
```

Extract and use the archive only after a match. Stop on a mismatch; do not skip validation or borrow checksums from another version. This release does not require deleting `.wcode`, clearing authorization records or rewriting project manifests. Do not overwrite an installation with unrelated uncommitted development source.

## Jobs: find, inspect and cancel a task

Press **W** in the running TUI to open the protected Project Status, select the relevant workspace, and open the job area under **Task activity**.

1. Select **Refresh retained jobs**. Discovery reads existing records; it does not start a command.
2. Combine task-state and UI/MCP-origin filters. They affect only the bounded response already loaded. No matching record does not mean there are no background processes or that a complete history is empty.
3. Select the exact `TASK-…` ID and inspect origin, status, command outcome, exit code and `stdout`/`stderr`. Observe truncation and redaction markers. `completed` means the task ended, not that checks or Acceptance passed.
4. Use **Refresh exact task** to read the selected task again without rerunning its command. This also resumes observation after it pauses because the page is hidden, you leave the activity view, or its polling budget is exhausted.
5. Cancellation appears only for a running **UI-owned** job that the server currently permits you to cancel. Viewing an MCP-origin job does not grant cancellation authority over it.

When cancellation is unconfirmed, refresh that same task ID before attempting another cancellation. Do not rerun the command just because a page is slow to update. Workspace or session changes invalidate old controls and replies; discover tasks again within the current scope.

## Check coverage of nested Rust projects

This fix concerns whether an independent project appears in the verification plan. It does not run duplicate checks for every Rust directory. Ordinary workspace members are covered by their owning root; a separately declared nested workspace has its own check scope.

Inspect discovered checks with `project_context` or `verification_plan`, including the directory attached to each command. Ask the Agent to call `verify_project` with `level: "full"` for complete verification. An independent project should have its directory represented rather than relying solely on a successful parent check. Rediscover and rerun after changing manifest boundaries; an older plan is not current evidence.

Both `[workspace]` and inline `workspace = {}` are top-level Cargo declarations. Do not put the inline form inside `[package]` or change the real project relationship merely to obtain a passing result.

## Troubleshooting

| Symptom | Action |
| --- | --- |
| The interface still looks old after updating | Check the executable path and the new process version, then reconnect the Host. Restart a standalone service only after inspecting active work. |
| Job discovery is unavailable | Keep the error visible, check connectivity/session, and repeat the read. An error is not an empty task list. |
| A task completed but verification remains blocked | Inspect exit code, failed checks, current revision and Acceptance requirements. Task lifecycle is not an acceptance decision. |
| A task cannot be found | Clear filters and refresh. Retention and access are bounded; do not guess identities or change ownership to reach a record. |
| No cancellation button | Check that the task is UI-owned, still running and server-authorized. Do not broaden permissions to bypass that boundary. |
| A check timed out or output is incomplete | Preserve `timed_out`, `output_incomplete` and the task ID. Read its terminal state/logs instead of submitting duplicate work as a polling substitute. |
| A nested Rust project is missing from the plan | Inspect its actual Cargo manifest boundary and command directory, then rediscover. Preserve missing/failed results instead of relying on historical success. |
