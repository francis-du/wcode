# v0.6.2 — Faster work, simpler setup, clearer observability

This is the 0.6.2 release preparation. Updating source versions and building locally do not publish a GitHub release. Cross-platform CI, artifact smoke checks and publication are separate gates. The existing v0.6.1 tag and its artifacts are not rewritten.

## Focused repository understanding

Explicit file-and-line diagnostics enter `agent_context` before broad symbol discovery. Source text, line ranges and SHA edit preconditions remain visible, including for supported non-code files. Missing or inaccessible anchors are reported rather than replaced with an unrelated edit target. Simple location queries defer unnecessary repository-map expansion; callers, impact and explicit scope requests retain the deeper path.

Exact symbol matches are ranked before broad keyword matches, and repeated matches do not clone the same candidate for every keyword. Concurrent cold requests for one file share the index build; unrelated files remain independent. `symbol_context` checks that symbol metadata and returned source belong to the same file version, retries a stale index once, and fails explicitly when a stable view cannot be obtained.

## Useful parallelism and command diagnostics

The blocking-pool ceiling, foreground resource budget and bounded file-I/O workers are coordinated instead of treating the outer tool-slot count as actual throughput. Queued execution requests leave controlled headroom for non-execution tools. Fixed-form Git inspections have a separate bounded process queue, so waiting for compiler capacity does not automatically block them.

Independent file mutations use a shared bounded I/O pool; SHA checks, original edit ranges, atomic per-file writes and ordered partial outcomes remain intact. The tested wider-pool read experiment was not retained because it did not improve that workload. No universal speedup percentage or peak-slot target is claimed.

Command timeout results retain collected diagnostics and expose `timed_out`, `output_incomplete` and retry guidance. Cancellation owns the child process and output readers; a timeout does not imply rollback and does not automatically replay a mutation. Output capture remains bounded; full head-and-tail retention for oversized command logs is not implemented in this release.

## Verification and evidence

Full verification accounts for every inferred check rather than silently truncating a mixed-language plan. Failed phases stop later work by default; supported schemas also expose full diagnostic mode. Incomplete acceptance checks cannot mint a passing acceptance result, and a language-quality check cannot stand in for whole-project verification.

Verification-history queries share one request-scoped revision and evidence snapshot across plans instead of rescanning for each plan. Empty history does not scan source or evidence. A later request sees edits and new evidence; no stale cross-request result cache was added. Plans shown as current must match both code and Design State.

The Observatory separates historical records from effective current-revision results. Retry replacement is scoped by target, kind, producer, model, confidence, target set and policy; equal-time conflicting results retain failure. Narrow checks do not clear wider failures. Bounded evidence details show the check, producer, provenance, time and recorded diagnostic summary. Missing evidence and truncated observations never prove success.

## Simpler configuration and explicit approval

`wcode help-all` exposes every built-in CLI command and parameter, including hidden advanced options, short flags, aliases, declared defaults and enum choices. Use `wcode help-all setup` to focus on one command or `wcode help-all --json` for a machine-readable catalog. It derives from the real parser, marks global and compatibility behavior, and never starts services or executes the selected command. Standard help remains compact and links to this entry; this is not an MCP tool catalog or an external-program authorization grant.

`balanced`, `fast` and `light` combine the common resource settings while advanced overrides remain available. Preview the installation without changing files:

```bash
wcode setup --performance fast --dry-run
wcode --show-config
```

Run `wcode setup --performance fast` to persist the reviewed launch options. Host-specific JSON and TOML installers preserve those options and unrelated servers; a concurrently changed configuration fails its SHA precondition instead of being silently replanned. Invalid or contradictory overrides fail before writing.

Common supported Git lifecycle operations can request exact human approval instead of being permanently rejected. Approval does not grant full access. A file-read-only mode is not a no-side-effects guarantee for commands; the view-only combination is `--read-only --no-exec --no-semantic`.

## A clearer Project Observatory

The first screen separates execution, pending approval, working-tree changes and effective verification. Searchable component cards and an inspector are the primary architecture view; Design / Implementation / Overlay dependency graphs remain available. Detailed requirements, files, history and provider information are progressively disclosed.

Activity polling is independent of slow project refreshes, including initial loading. Busy activity uses a two-second completion-to-next-request interval; idle activity and project checks use eight seconds. Hidden tabs stop read polling. Shared process resources are labeled separately from workspace tasks, and unknown measurements are not zero or idle.

All access mutations bind the workspace and selection generation, suppress duplicates and ignore obsolete responses. Semantic refresh follows the same selection-generation rule. A stale revision response cannot undo a newer approval list. Network and server-side write failures require checking actual state before retrying; no mutation is automatically replayed. Evidence-only changes trigger refresh using bounded metadata identities without decoding every stored evidence body.

## Upgrade and compatibility

After publication, use `wcode update`, then restart or reconnect the relevant MCP host so it launches the new executable and reloads tool schemas. Building the repository does not replace an installed executable or restart an existing process. Existing workspace boundaries, exact approval and persisted-state formats remain in place.

Only use new optional fields, including `parallel_tools.dry_run`, when the running tool schema advertises them. An older runtime ignoring an unknown field is not a safe preview. A plan preview checks scheduling, not authorization or file preconditions, and does not execute tasks.

The research roadmap is not a delivered independent model CLI, browser agent or PTY subsystem. No claim of complete replacement of another coding agent is made. Real-browser visual/accessibility acceptance and cross-platform results must be reported from actual runs, not inferred from JavaScript fixtures or local Rust tests.

## Release gates

Cargo, Cargo.lock and all six marketplace/plugin manifests identify 0.6.2; dependency versions are unchanged. The CI test matrix explicitly installs Node 24 for JavaScript behavior regressions. Windows packaging checks each native build/smoke exit code and verifies the staged binary's version before creating an archive.

Before tagging `v0.6.2`, run the same locked quality gates as CI:

```text
git diff --check
cargo check --locked
cargo fmt --check
cargo test --locked
cargo clippy --locked --all-targets -- -D warnings
cargo build --release --locked
```

Validate Design State, traceability and project conventions. Inspect current-revision persisted evidence separately from successful command output; an old record does not establish this version's verification. Run the Linux/macOS/Windows matrix and distribution signing, checksum and installer gates before claiming release success. Do not move a previously published tag.
