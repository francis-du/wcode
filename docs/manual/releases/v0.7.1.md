# v0.7.1 — Resilient tunnels, real-time project loading, and stronger parallel execution

v0.7.1 is a stabilization and throughput release. The release candidate is committed and pushed first; the `v0.7.1` tag is created only after the normal CI for that commit is green. Tag-triggered cross-platform packaging and publication remain a later gate.

## Tunnel, Host trust, and network recovery

Tunnel lifecycle is now stateful instead of treating every failed probe as a dead endpoint. A standby can become suspect or quarantined without immediately killing its provider process or unregistering its Host. Stable aliases are retained while the public endpoint still resolves to the current wcode instance, and provider-process failure is no longer identical to endpoint failure.

Public health checks are tolerant of short network jitter: the normal path still performs one fast probe, while a failure receives two short confirmation retries before it is counted as a real failure. Recovery probes run quickly, stable Host trust survives transient transport loss, and bounded backoff plus provider-specific jitter prevents reconnect storms during sustained outages.

Tailscale Funnel remains the preferred stable zero-configuration endpoint. Microsoft Dev Tunnels are now supported as an explicit persistent provider through an existing tunnel ID; account/login/tunnel creation stay operator-owned, so Dev Tunnels are not added to `auto`. Temporary Cloudflare, localhost.run and Pinggy endpoints remain useful fallbacks but are not treated as durable identities.

## WebUI project loading is real-time again

Engineering Observatory project state now uses stale-while-revalidate behavior. A cached per-project snapshot can render immediately while revision-aware refresh work runs asynchronously. Switching projects no longer clears the entire view and waits for a full synchronous Observatory rebuild when a usable snapshot already exists.

Revision checks, project snapshots and activity refreshes are separated so the UI can show useful state first and converge afterward. Cached data remains generation-bound and revision-aware; stale responses cannot overwrite a newer project selection.

## Faster coding and stronger parallel execution

Parallel-first behavior is now a canonical engineering constraint rather than optional prompt guidance. Independent discovery, reads, file-local edits and verification lanes should fan out; serialization requires a real data or path dependency. `agent_context` carries this constraint so downstream coding agents see it in the same bounded context used for implementation.

The scheduler has a read-only fast path that avoids pairwise conflict-graph work for pure fan-out. Workspace revision computation reuses one file scan for code and Design State in the normal case. Foreground resource limits now emphasize real throughput: up to 32 tool slots, 32 bounded file-I/O lanes, up to 8 lightweight probe processes, adaptive 4–8 Tokio workers, and heavy child-process capacity derived from memory plus CPU-thread headroom instead of a fixed low ceiling. Background sustained CPU remains governed separately.

`balanced`, `fast` and `light` remain the supported resource presets. They still control bounded capacity rather than promising unlimited concurrency.

## Development tools no longer ask for repetitive authorization

Known development toolchains across all 22 indexed languages now receive command-specific autonomous policy for normal local development: compile, test, lint, format, typecheck, build, dependency maintenance and repository-declared verification runners can execute without repeated human approval when their arguments stay inside the hardened shapes.

The boundary is still strict. Shell interpreters, arbitrary inline eval, credential redirection, host-wide toolchain changes, force/history rewrites, release publication, destructive infrastructure actions, compiler/plugin/agent injection and unsafe path escapes remain blocked or separately authorized. The safe inspection-only combination remains:

```text
--read-only --no-exec --no-semantic
```

## `semantic_auto` stops retrying fake providers

`semantic_auto` no longer treats a rustup proxy named `rust-analyzer` as launch-ready when the active Workspace toolchain does not actually contain the `rust-analyzer` component. Discovery validates the proxy, caches viability briefly, and reports the provider as unavailable instead of repeatedly spawning a known-broken server and generating an error storm.

Warm semantic sessions, syntax fallback and explicit authorization for non-hardened providers remain unchanged. Provider failures continue to distinguish discovery, authorization, spawn, initialize, protocol and live states.

## Diagnostics and compatibility

Command timeout and cancellation diagnostics continue to expose `timed_out` and `output_incomplete`; cancellation still does not imply rollback or automatic replay. OAuth, Workspace isolation, Design State, Evidence, repository SHA guards and no-shell execution remain compatible with 0.7.0.

Use `wcode help-all`, `wcode help-all setup` and `wcode help-all --json` to inspect the complete parser-defined CLI surface without executing the selected command.

All six Plugin/Marketplace manifests, Cargo and Cargo.lock identify 0.7.1. CI continues to install Node 24 for JavaScript Observatory behavior tests and runs the RustSec dependency audit before release packaging.

## Verification and release gate

Before pushing the 0.7.1 release candidate, run the locked local gate:

```text
git diff --check
cargo check --locked
cargo fmt --check
cargo test --locked
cargo clippy --locked --all-targets -- -D warnings
cargo build --release --locked
```

Also validate Design State, Product Scope and repository conventions. After the commit is pushed, wait for CI on that exact commit to pass. Only then create `v0.7.1`; the tag-triggered release workflow performs Linux/macOS/Windows build, smoke, signing/packaging and publication gates. Do not create or move the tag before CI is green.
