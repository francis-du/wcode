# wcode v0.5.0

v0.5.0 is a semantic-runtime milestone. wcode no longer treats first-party LSP support as an occasional index refresh that starts a language server, asks a bounded set of questions, and shuts it down. Hardened providers can now stay warm inside a bounded Workspace-scoped session, and coding agents get an explicit `semantic_navigation` surface for the relationship questions where text search and syntax indexing are incomplete.

The important change is not “more LSP calls.” The default coding path is intentionally task-adaptive: Tree-sitter and repository search remain the cheap localization layer, while warm semantic sessions are used when references, implementations, callers, callees, hover/definition resolution, or cross-file impact need stronger completeness.

## Warm Semantic Runtime

- Hardened first-party semantics are enabled by default. `rust-analyzer` is the first provider with an automatic safety profile.
- The Harness owns a bounded **warm session** pool keyed by Workspace, provider identity, and provider-binary identity.
- Background semantic graph maintenance and foreground `semantic_navigation` reuse the same live provider session instead of launching parallel copies.
- A session serializes one JSON-RPC protocol stream per slot and has real capacity/idle bounds. Idle pruning removes only unleased slots; capacity eviction never drops an active lease; an all-busy pool fails closed; and provider-binary replacement waits for the old leased slot to finish before rebuilding.
- Document state is revision-aware and server-driven: wcode honors the advertised `textDocumentSync` Full / Incremental / None mode, sends `didChange` only in a supported form, computes valid incremental replacement ranges in the negotiated position encoding, and sends open/close notifications only when requested.
- Automatic workers operate only on the most-specific discovered project Workspaces, use a stable-source window and bounded retry, and acquire the same global Harness concurrency boundary as model-facing work.
- Semantic graph facts still carry source revision provenance. Stale facts stop participating in graph overlays, impact, reconciliation, and context until fresh provider evidence exists.

## 22-language LSP conformance

v0.5.0 also tightens the meaning of “supported language.” The 22 syntax-indexed languages now each have exactly one canonical LSP launch profile covered by deterministic compatibility tests; every canonical profile also spawns a real stdio mock-LSP process and completes wcode's `initialize` framing/capability handshake. Provider-specific commands and workspace arguments are part of that contract rather than informal registry strings.

- Bash uses `bash-language-server start`; C/C++ use `clangd`; C# uses `csharp-ls`; CSS/HTML use the VS Code language servers over `--stdio`.
- Dart uses `dart language-server --protocol=lsp` with wcode client identity; Go uses explicit `gopls serve`.
- Elixir recognizes the ElixirLS `language_server.sh` / Windows wrapper and common `elixir-ls` distribution wrapper.
- Java starts `jdtls` with a unique user-state `-data` directory per Workspace/runtime so parallel project sessions do not share JDT LS state.
- JavaScript/TypeScript/TSX use `typescript-language-server --stdio`; Lua uses `lua-language-server`, with symlink-aware launch handling for LuaLS relative-resource discovery.
- OCaml/interface use `ocamllsp`; PHP uses `phpactor language-server`; Python uses `pyright-langserver --stdio`; R uses `R --no-echo -e languageserver::run()`; Ruby uses `ruby-lsp`; Rust uses `rust-analyzer`; Swift uses `sourcekit-lsp`.
- The old OmniSharp `-lsp` fallback is no longer counted as a reliable C# path. Real alternates remain only where they are useful: Intelephense for PHP, pylsp for Python, and Solargraph for Ruby.
- Foreground `semantic_navigation` and manual semantic refresh both try an installed alternate when the canonical provider exists but fails live initialization. Alternate authorization stays provider/binary-specific, and refreshes report a successful switch in `fallbacks`.

Compatibility is not the same thing as installation. The deterministic 22-profile handshake verifies wcode's adapter/transport contract; wcode does not bundle 22 external language servers and never reports a missing executable as semantic support. Provider status now makes the transition machine-readable: `available` means an executable candidate exists; `launch_ready` means execution/policy/trust allow it to start; `session_validated` means that exact provider binary completed live LSP initialization; only then is `runnable=true` and semantic precision active. A provider becomes real semantic evidence only after that validation and a response for the current source revision; otherwise the runtime stays explicit about unavailable/pending/failure state and preserves syntax fallback.

## Agent-native semantic navigation

`semantic_navigation` is designed for agents rather than exposing raw LSP offsets as the primary API.

- Prefer `path + symbol`. wcode resolves the symbol with its Tree-sitter index, then converts the 1-based UTF-8 byte position into the position encoding negotiated with the language server.
- Callers that already own a precise source position may still use `line + character`.
- Supported intents cover semantic definition/hover, references, implementations, incoming calls, outgoing calls, combined call relationships, and a bounded impact bundle.
- UTF-8 and UTF-16 position conversion is explicit and tested, so an agent does not need to guess language-server character offsets.
- Results are bounded, deduplicated, and filtered back through the canonical Workspace boundary before they reach the model.
- `unsupported` and `failures` are separate. A supported request that successfully finds no relationships returns an empty list; an LSP error/timeout is surfaced as failure and is never treated as negative semantic evidence.
- If no trusted semantic provider can run, wcode returns an explicit syntax fallback instead of pretending Tree-sitter facts have semantic precision.

The normal routing rule is deliberately asymmetric:

```text
localize a symbol/file
  → find_symbol / search_code / Tree-sitter

need cross-file relationship completeness
  → semantic_navigation
  → reuse warm LSP session
```

This keeps simple tasks cheap while making semantic relationships available when they materially improve correctness.

## Safety and trust boundaries

Default-on semantics does not mean blanket trust for every language server.

- Only providers with a built-in hardened automatic profile may enter the default semantic lane. In v0.5.0 that means `rust-analyzer`.
- The provider executable must resolve outside the Workspace. Repository-local language-server binaries are rejected.
- Sensitive credentials and execution-injection environment variables are scrubbed before provider launch.
- The `rust-analyzer` initialization profile disables build scripts, proc macros, Cargo auto-reload, and check-on-save to reduce repository-controlled code execution.
- The warm session pool remains bounded and result-side Workspace filtering is mandatory even after a provider has been trusted.
- `--no-semantic` disables all first-party language-server execution and keeps syntax fallback available.
- Providers without an automatic profile remain an explicit trust expansion. They require provider-session `RiskyExecution` approval, or the operator may deliberately use process-wide `--allow-risky-exec`.
- A provider-session authorization binds Workspace + Provider + current provider-binary identity. Refresh/navigation may reuse only that exact warm provider; replacing the executable invalidates the old grant.

These controls reduce the default execution surface; they are not an OS sandbox. A language server can still parse repository metadata and configuration, so non-hardened providers stay outside the automatic lane.

## Task-adaptive routing and observability

v0.5.0 also changes when semantic work is recommended and how operators can tell whether it is paying off.

- `agent_context` detects relationship-oriented tasks such as references, callers, implementations, rename impact, and cross-file semantic impact. It recommends `semantic_navigation` only when stronger relationship evidence is useful.
- Ordinary “where is this symbol?” work stays on Tree-sitter/search instead of paying LSP startup or query cost.
- The TUI Intelligence view exposes warm-session count, synchronized document count, provider starts, semantic query count, and fresh/stale semantic provider state.
- The live dashboard now owns terminal output while its alternate screen is active. Tunnel/provider retries, dependency checks, reconnects, Setup-browser diagnostics, and other background operator messages are routed through `TaskMonitor` instead of writing directly to stdout/stderr; provider installers are captured rather than inheriting the terminal. This prevents background tunnel text from floating over or corrupting the ratatui frame.
- Cached graph inputs can avoid graph reconstruction while still warming the provider session so later semantic requests do not pay process startup cost.
- High-value Call Hierarchy and Implementation expansion remains bounded rather than querying every variable, field, and low-value symbol.
- `semantic_provider_refresh` remains available as a force-refresh surface; automatic maintenance is the default for the hardened lane.

## Compatibility and upgrade

There is no Workspace or Design State migration for v0.5.0.

Install the current release with the normal installer:

```bash
curl -fsSL https://raw.githubusercontent.com/francis-du/wcode/main/install.sh | sh
```

A running v0.4.x process must be restarted before it can expose the v0.5.0 Tool schema, warm-session runtime, and default semantic policy:

```bash
wcode restart
```

Existing local `mcp-stdio` configuration and remote `/mcp` OAuth connections keep the same transport contract. `--no-semantic` is available when an operator wants the previous syntax-only execution posture.

The portable Agent Plugin manifests and marketplaces are versioned with the crate. Release preparation now unit-tests both plugin manifests and marketplace version fields against `CARGO_PKG_VERSION`, while the tag workflow independently verifies the same release metadata.

## Release gates

v0.5.0 is a milestone release and should be claimed only from the tagged revision that passes the complete release pipeline.

Local preparation requires:

```text
git diff --check
cargo check --locked
cargo fmt --check
cargo test --locked
cargo clippy --locked -- -D warnings
cargo build --release --locked
```

Repository governance must also remain green: valid Design State, complete Requirement → Component / Design → Implementation / Acceptance → Verification traceability, zero required Convention failures, complete Product Scope mapping, and bilingual documentation parity.

The GitHub release workflow independently runs the governance check, Clippy across all targets, installer syntax validation, tests on Linux/macOS/Windows, optimized platform builds, binary version checks, archive generation, and SHA-256 checksums before publishing release assets. Local green evidence is release preparation; the published tag and CI artifacts are the final release evidence.
