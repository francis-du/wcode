# v0.7.0 — Architecture-first observability and faster engineering control

This page accompanies the 0.7.0 release preparation. Updating source versions and building locally do not publish a GitHub release. Tagging, cross-platform CI, package signing, installer smoke tests and publication remain separate operator-controlled gates.

## Engineering Observatory rebuilt around the system

The protected Engineering Observatory is now a real workspace instead of one long dashboard. One global bar owns project search, Workspace selection, live state, refresh, language, theme, semantic refresh and access management. Seven primary tabs separate Overview, Engineering architecture, Task activity, Verification evidence, Current changes, Requirements and Project files.

Architecture is the primary system view. The default System Map reads top-down through semantic layers and keeps dependency detail in inspectors and ledgers instead of drawing every edge at once. Subsystem cards expose bounded ownership facts, state and scale; selecting one opens an inspector with upstream/downstream relationships, evidence and coverage. Components and exact dependency evidence remain available as drill-down views. Fit and Full Map are real viewport operations rather than cosmetic scale toggles.

Verification uses a ledger plus inspector instead of mixing current proof, historical results and diagnostics into one page. Requirements expose requirement → component → code → verification → evidence traceability. Current Changes exposes impact and convergence separately from raw diff rows. Activity, Files, Diagnostics and Language Quality use the same readable hierarchy and keyboard/focus contracts.

## Faster project-state loading

Initial Observatory loading no longer waits on the revision request before starting the project snapshot request. Revision and project observations are issued concurrently, while activity remains on its own polling path. Inside the Harness, independent Observatory work is grouped into parallel stages instead of one long serial chain where every repository analysis waits for the previous one.

The change does not weaken freshness rules: stale responses remain generation-bound, later revision polling still invalidates the full project snapshot when required, and no speedup percentage is claimed without a measured workload. Expensive repository work remains bounded by the same Workspace and Harness resource limits.

## Agent Context, bounded execution and diagnostics

`agent_context` remains the default coding entry point. Exact targets, Design State, code relationships, tests, revision state, SHA edit preconditions and verification references stay ahead of broad repository context under tight budgets. Ambiguous work can still grow within the bounded context budget, while mixed intent deliberately falls back to balanced routing instead of pretending confidence.

Independent work should use concurrent top-level calls when the Host supports them; bulk `read_files`, `search_many`, `apply_file_edits` and `create_files` remain the compact path for known targets. `parallel_tools` keeps dependency-aware scheduling rather than becoming an unrestricted race-everything primitive.

Command timeout diagnostics retain captured output and expose `timed_out` and `output_incomplete`. Cancellation does not imply rollback and does not replay mutations automatically. Human approval remains exact and operation-scoped.

## Configuration and compatibility

`balanced`, `fast` and `light` continue to provide the common resource profiles while advanced overrides remain available. Preview setup without changing files:

```bash
wcode setup --performance fast --dry-run
wcode --show-config
```

Use `wcode help-all`, `wcode help-all setup` and `wcode help-all --json` to inspect the complete parser-defined CLI surface without executing the selected command.

File read-only mode is not a no-side-effects command guarantee. The view-only combination remains:

```text
--read-only --no-exec --no-semantic
```

Existing Workspace isolation, OAuth state boundaries, exact authorization, persisted Evidence and Design State formats remain compatible. Restart or reconnect an MCP Host after updating so it launches the new executable and reloads schemas.

## Release packaging and CI

Cargo, Cargo.lock and all six marketplace/plugin manifests identify 0.7.0. The quality job also audits Cargo.lock against the RustSec Advisory DB, with repository declaration in `.cargo/audit.toml`; vulnerabilities block the release while automatic issue creation stays disabled. The test matrix explicitly installs Node 24 for JavaScript Observatory regressions. Linux, macOS and Windows artifacts are built only after quality and test jobs succeed; distributed binaries run `--version` and `--help` smoke checks before packaging. macOS distributed binaries are re-signed after post-link changes, installers stage and smoke-test before replacement, and published archives receive SHA-256 checksums.

Before tagging `v0.7.0`, run the locked repository gate:

```text
git diff --check
cargo check --locked
cargo fmt --check
cargo test --locked
cargo clippy --locked --all-targets -- -D warnings
cargo build --release --locked
```

Validate Design State, traceability, Product Scope and the current change review. Current-revision Evidence must be inspected independently from successful command output. A local green build does not claim Linux/macOS/Windows packaging success until the release workflow actually runs. Do not move an already-published tag.
