# wcode v0.9.1

**2026-10-23 发布的维护版本。** 本版更新任务活动界面、修复独立 Cargo 工程漏检，并维护 TLS 和 macOS 依赖。命令授权规则与受保护路径边界没有放宽；WTeam 的支付、企业身份和数据库不随本版部署。

[正式版本与下载](https://github.com/francis-du/wcode/releases/tag/v0.9.1) · [完整代码差异](https://github.com/francis-du/wcode/compare/v0.9.0...v0.9.1) · [首次安装](../../getting-started/) · [CLI 与 MCP 参考](../../reference/)

## 更新内容与影响

| 更新 | 对使用者的影响 |
| --- | --- |
| 保留任务的状态与 UI/MCP 来源筛选 | 快速找到已返回的任务，显示匹配数和保留记录数；不冒充完整进程历史。 |
| 工作区、会话、任务绑定的刷新与取消 | 切换到任务 B 后，任务 A 遗留的按钮不能取消 B；迟到回复和已排队的轮询不能覆盖新选择。 |
| 独立嵌套 Cargo workspace 发现 | 显式 `[workspace]` 和顶层内联 `workspace = {}` 都保持独立检查范围，不再仅因语言相同而被父工程吞掉。普通成员仍由所属 workspace 覆盖。 |
| TLS 依赖补丁及 macOS 依赖裁剪 | 更新锁定的 TLS 验证依赖，关闭菜单栏未使用的 X11/Wayland 默认特性，保留原生窗口句柄支持。 |
| 跨平台测试隔离 | sandbox 测试在新子进程中建立私有状态目录，避免依赖其他测试的运行顺序；生产环境缺失受保护目录时仍拒绝运行。 |

## 已安装用户：升级后还要重新连接

先保存正在进行的工作，确认需要保留的任务状态，再在终端执行：

```bash
wcode --version
wcode update
wcode --version
```

`wcode update` 使用当前安装位置更新，获取的是执行时的最新正式版本，**不是固定版本选择器**。要精确安装 v0.9.1，使用上面的固定版本下载页并核对校验和。不要添加并不存在的 `wcode update --version ...` 参数。

升级完成后，重新连接本机 MCP Host，使它重新启动 `wcode mcp-stdio`。旧 stdio 会话仍运行原来的进程，磁盘上的文件更新不代表当前会话已经升级。独立 TUI／HTTP 服务也需要操作者在确认任务状态后自行重启；安装器不会替你迁移正在执行的任务。

Windows 的更新辅助程序在当前更新进程退出后才替换文件；看到“准备更新”不等于已经完成。辅助程序结束后再检查版本。新启动的终端命令应报告 `wcode 0.9.1`，但这仍不能单独证明旧服务已重启。

出现不同版本时，Unix 可用 `command -v wcode`、PowerShell 可用 `Get-Command wcode` 检查命中的安装位置，再核对 Host 保存的可执行文件路径。不要通过删除权限状态或重新授权全部目录来处理版本问题。

## 手动下载与完整性核对

| 平台 | 归档 |
| --- | --- |
| Linux x86_64 | `wcode-linux-x86_64.tar.gz` |
| macOS Apple Silicon | `wcode-macos-aarch64.tar.gz` |
| macOS Intel | `wcode-macos-x86_64.tar.gz` |
| macOS 通用包 | `wcode-macos-universal.tar.gz` |
| Windows x86_64 | `wcode-windows-x86_64.zip` |

从同一 v0.9.1 发布页取得对应归档及 `SHA256SUMS`，计算文件的 SHA-256，与清单中**同名文件**的完整值比较。例如：

```bash
# Linux
sha256sum wcode-linux-x86_64.tar.gz
# macOS Apple Silicon
shasum -a 256 wcode-macos-aarch64.tar.gz
```

```powershell
Get-FileHash .\wcode-windows-x86_64.zip -Algorithm SHA256
```

只有匹配后才解压使用。不匹配时停止，不跳过校验，也不从其他版本借用校验和。本版没有要求删除 `.wcode`、清空授权记录或修改项目清单；不要把未提交的开发源码覆盖进安装目录。

## Jobs：定位、读取与取消任务

在运行中的 TUI 按 **W** 打开受保护的 Project Status，选中具体工作区，进入**任务活动（Task activity）**中的任务区域。

1. 点击**刷新保留任务（Refresh retained jobs）**。该操作读取已存在的任务，不创建新命令。
2. 组合使用任务状态和 UI/MCP 来源筛选。筛选只作用于本次返回的有界记录；“没有匹配项”不代表没有后台进程或完整历史为空。
3. 选择准确的 `TASK-…` ID，检查来源、状态、命令结果、退出码及 `stdout`／`stderr`。输出可能有截断或脱敏标记；`completed` 只表示任务结束，不等于检查成功，更不等于 Acceptance 通过。
4. 用**刷新精确任务（Refresh exact task）**重新读取所选任务。它不重跑命令。自动观测因页面隐藏、离开任务页或次数上限而暂停后，可用这个入口继续读取。
5. 只有当前服务端允许取消的 **UI 所属运行任务**才显示取消按钮。MCP 来源任务可以查看，但不能借这个页面取得它的取消权限。

取消回执不确定时，先刷新**同一个任务 ID**确认状态，不能因为页面没有及时更新就重复取消或重新执行。切换工作区或会话后，旧按钮与旧请求失效；重新发现当前范围内的任务即可。

## 检查嵌套 Rust 工程是否被覆盖

本版修复的是“验证计划是否包含独立工程”，不是让所有 Rust 子目录重复运行检查。根 workspace 的普通成员由根检查覆盖；声明为独立 workspace 的嵌套工程有自己的检查范围。

通过 `project_context` 或 `verification_plan` 查看实际发现的检查，核对命令所对应的目录；需要完整验收时让 Agent 调用 `verify_project`，选择 `level: "full"`。独立工程应出现对应目录的检查，而不仅是父工程的一条成功结果。清单边界改变后应重新发现和验证，不能继续使用旧计划。

`[workspace]` 与内联 `workspace = {}` 都是 Cargo 清单的顶层声明；不要把后一种写进 `[package]` 表，或为了让检查通过而随意改变实际项目关系。

## 常见问题

| 现象 | 处理方式 |
| --- | --- |
| 升级后界面仍旧 | 核对安装路径和新进程版本；重新连接 Host。独立服务由操作者确认任务状态后重启。 |
| 任务发现不可用 | 保留错误状态，检查连接／会话，重新读取；不要把错误当作空列表。 |
| 任务已完成但验证仍阻塞 | 查看退出码、失败检查、当前代码版本及 Acceptance 要求；任务生命周期不是验收结论。 |
| 找不到某个任务 | 清除筛选并刷新；记录有保留上限和权限范围，不通过猜 ID 或改变归属来访问。 |
| 取消按钮没有出现 | 核对是否 UI 来源、仍在运行且服务端允许取消；不扩大权限来绕过限制。 |
| 检查超时或输出不完整 | 保留 `timed_out`、`output_incomplete` 和任务 ID，先读终态与日志，不能用重复启动代替查询。 |
| 独立 Rust 工程未出现在计划中 | 核对实际 Cargo 清单边界及执行目录，再重新发现；保留失败与遗漏信息，不用历史通过兜底。 |

使用 `wcode help-all`、`wcode help-all setup`、`wcode help-all --json` 查看完整命令，而不启动运行时。WTeam 的开发工作、Stripe 配置、真实客户联调及本地未提交改动不包含在此版；发布成功也不表示你的本机服务已自动升级。
