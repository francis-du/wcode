# v0.8.3 — 能力感知 MCP 与编辑就绪 Agent Context

v0.8.3 继续推进无需 IDE 的工程运行时：在不削弱执行与安全边界的前提下，让模型更容易使用大规模 MCP 工具面。本版本加入能力感知的渐进披露、更紧凑且任务定向的 `agent_context`、独立 Jev Policy、现代 MCP Task 兼容，并把发布对抗审计提升到 300 个不同轮次。

## 能力感知 MCP 发现

- MCP Catalog 保留完整工具面，同时暴露精简 Core 与有界的按需 Capability Group。
- `agent_context` 现在携带任务定向的 recommended tools / actions，让模型优先发现下一步真正有用的能力，而不是每轮都在完整工具目录中选择。
- 核心安全控制保持不可让渡：Workspace 边界、授权、SHA precondition、writer lease 与 verification authority 都不会交给模型提示自行决定。
- MCP discovery 与 server instructions 保持模型无关，并通过兼容层扩展能力，而不是按特定客户端隐藏工具。

## 更紧凑的编辑就绪 Agent Context

- 紧预算下优先让 advisory prose、大型 relationship overlay、已由当前源码覆盖的重复 map metadata，以及可选工具元数据让位于真正的编辑输入。
- 多个显式目标在请求源码本身能够放入预算时，可在 2K 路径继续保留完整 source body 与匹配的当前 SHA precondition。
- 普通压缩阶段保留最强 repo-map 证据；只有当完全相同的当前 identity 与完整源码已经交付时，relationship-free 的重复条目才允许让位。
- Compaction 有明确步数上限，并要求真实 serialized-byte progress；已经足够紧凑的 Execution 状态不会被替换成更大的摘要。

## Jev 与验证权限

- Jev routing policy 从 transport/runtime plumbing 中拆分，继续严格保持 advisory-only。
- Jev 可以增加有界的检索或验证工作，但不能删除 deterministic check、授予 mutation authority，或降低已有 verification floor。
- Verification Mesh 继续把 deterministic、property、mutation、fuzz、runtime canary、blind review 与显式 human approval 绑定到精确 revision。

## MCP Task 与运行时可靠性

- 现代 MCP Task capability 按请求协商；durable task 可轮询、可取消、按 owner 隔离，并可恢复而不会重放已经完成的副作用。
- Cancellation 在底层 worker 真正退出之前继续占用真实 worker/admission capacity，避免“逻辑取消但资源仍泄漏”。
- Command 结果继续显式暴露 `timed_out` 与 `output_incomplete`，不会把有界执行失败包装成假成功。
- Resource governance 保持前台工程工作响应性，同时继续执行 Host 全局与 Workspace 级资源上限。

## 发布审计

发布审计现在要求 300 个不同的 adversarial round。每轮都必须实际执行 non-zero Rust tests 并报告 stable inputs；分片与完整套件在进入发布批准前必须绑定同一个 exact revision 与 input digest。

主要的有界编码入口继续是 `agent_context`。资源预设仍为 `balanced`、`fast`、`light`，JavaScript 行为 CI 使用 Node 24。

CLI 发现继续保持无副作用：

```text
wcode help-all
wcode help-all setup
wcode help-all --json
```

强化后的纯检查组合仍为 `--read-only --no-exec --no-semantic`。最终 Rust 发布验证包含：

```text
cargo test --locked
cargo clippy --locked --all-targets -- -D warnings
```

## 发布验证

v0.8.3 候选必须通过 locked fmt/check/clippy/test/release-build、Design／Traceability／Drift／Risk 审查、release metadata 与 installer contract、Verification Mesh、runtime canary、blind reviewer、策略要求的显式 human approval，以及 clean-worktree 300 轮 adversarial audit，之后才允许打 tag。

发布流程保持：reviewed release-prep commit → 非强推 push → 精确 SHA CI 全绿 → `v0.8.3` tag → 跨平台产物、checksums 与 GitHub Release。
