# v0.8.0 — Engineering Digital Twin

v0.8.0 继续推进 wcode 的核心目标：不依赖传统代码编辑器，也能理解、观测和监督一个软件系统。Engineering Observatory 升级为有界 Engineering Digital Twin，仓库扫描统一支持 Ignore 语义，WebUI 不再由浏览器反复触发重快照，TUI 改为任务优先，同时可校准 Decision Plane 继续服从确定性的安全边界。

## Engineering Digital Twin

Engineering Architecture 内新增 Code Graph 工作台，与 System Map、Components、Dependencies 并列为架构内部视图。它不是第八个顶层 Workspace：架构仍然是主心智模型，代码关系只是更深一层的可观测视图。

图谱支持有界 Calls、Impact、All Evidence 三种模式，可按符号搜索调用者、被调用者、引用、依赖、实现归属、测试、需求以及 Verification/Proof 上下文。探索有明确的深度、节点和边上限，并使用“上游 → 中心 → 下游”三段式布局，而不是无限扩张的节点球。

每个节点和关系都保留 provenance 与 precision。Declared、Syntax、Semantic/LSP、Runtime、Deterministic、Heuristic 不会被压成一个含糊的置信结论。Inspector 会解释“为什么这个节点相关”，显示方向、关系类型、Provider、精度，并标记它是否位于当前 Working Tree 变更中。

Code Graph 还可直接读取 Graph History。切换历史 Snapshot 即可进行只读时间旅行，查看过去版本的调用链、依赖与 Proof 上下文，不需要重新扫描仓库。

## 更快、更安静的 Observatory

同一个 Workspace 同时最多只有一个后台 Observatory 重快照。缓存响应携带 Revision Stamp，并明确区分 cached/current/refreshing。浏览器先展示可用缓存，再用轻量有界探测等待后台刷新，不再自己发起成组的重型快照请求。

WebUI 顶层严格保持 7 个 Workspace。Code Graph 位于 Engineering Architecture 内部。0.8 的能力卡片来自 Harness Runtime Capability，而不是前端写死的宣传文案。

所有可观测 Workspace 现在共享同一套视觉语法：Project Pulse 与状态是一眼层，指标、关系和时间线是第二层，Evidence 与 Inspector 是第三层。Overview、Digital Twin、Task Activity、Verification Evidence、Current Changes、Requirements 和 Runtime 使用一致的语义状态灯与状态边。支持/状态/Metadata 文案保持至少 12px，Stale、Unknown、Inconclusive、Failed、Unverified 不会在视觉上伪装成当前版本的 Passing Proof。

## Ignore 感知仓库智能

全仓 Source、Search、Index、Status 与 Subspace Discovery 统一使用 Ignore-aware Walker。默认遵守 .gitignore、.ignore、Git global/exclude 与受保护路径，并在遍历前剪掉 Rust target、node_modules、缓存和常见生成目录。

明确指定的 ignored path 仍可通过有界 Read/Search 查询。Project Profile 与 Contract Discovery 保留自己的可见性策略，避免把合法 build/codegen 配置误当生成噪声。

## 任务优先 TUI

宽终端使用 70/30 布局：Workspace Activity 是主画布，Engineering/连接状态进入右侧控制栏。控制栏压缩为 ARCH、DRIFT、PROOF、MODEL 四条独立语义线，Policy Error/Warning 会排在截断之前优先展示。中等和窄终端不再常驻 Engineering Pulse，任务行优先占据空间。I Engineering Console 继续作为 Architecture 与 Proof/Runtime 的深钻入口。

Pairing、授权、恢复控制、命令发现与极小终端回退仍保持可见且有界。

## 可校准 Decision Plane 与 Shadow A/B

Provider-neutral Decision Plane 输出有界 Probability、Choice、Score，但实际行为权限仍属于确定性的 Authorization、SHA 前置条件、Evidence 与 Verification。

Context Sufficiency 使用独立 Engineering Fitness Gold 带外校准，而不是拿 wcode 自己的 readiness 当真值。在当前 60 Case 不依赖模型的诊断中，1K cold/warm 的 Required Identity Recall、Complete Body Recall、Fresh SHA Recall 均为 100%，58/58 个可写 Eligible Case 都拿到了全部 Edit Inputs。Decision Baseline 仍为 Brier 0.018846，False Stop/False Continue 均为 0。

Provider Shadow A/B 在同一个不可变 DecisionRequest 上比较 baseline 与 candidate，并记录 shared/missing signal、数值差、Choice 分歧、Shape 异常与 Safety Policy Violation。Candidate 始终只有观测权。v0.8.0 不启用外部 Jev/System-One Provider。

## 检索、检查与运行时可靠性

Engineering Fitness 保留更低噪声的检索基线，并继续明确区分“定位到了”“拿到完整源码”“SHA 新鲜”“真正编辑就绪”。

有界 scan_patterns 提供 AST 验证的 Go Bug Pattern，包括 Nil Dereference 候选、吞掉 Error、Index Mismatch、Empty Test 与 Unguarded Subscript。扫描一旦截断，就不会声称全仓不存在问题。

会执行子进程的 Tool 会先获取 Execution Admission，再占全局 Tool Capacity，为非命令工作保留 Headroom。取消与队列继续 Fail Closed：取消的 Waiter 不得泄漏容量，已启动的 Blocking Work 持有 Permit 到结束，Cancellation 也绝不代表 Rollback。

## 兼容性与安全

v0.8.0 不新增必填 API Key，也不要求外部 Decision Service。现有 MCP Client 继续使用相同的 Workspace、Authorization、Protected Path、SHA 与 Verification 边界。

Engineering Digital Twin 是只读可观测层，不会创建第二份可变项目状态。Full Access 仍然只能由 Operator 明确选择，不能从 Decision Plane 输出或图关系推导。

兼容契约保持显式且可搜索：`agent_context` 继续作为有界 Coding Context 主入口；命令结果继续返回 `timed_out` 与 `output_incomplete`；资源预设仍为 `balanced`、`fast`、`light`；JavaScript 行为 CI 使用 Node 24；Hardened 只读组合仍是 `--read-only --no-exec --no-semantic`；审查后的发布门禁继续包含 `cargo test --locked` 与 `cargo clippy --locked --all-targets -- -D warnings`。

仅检查场景继续可以使用 --read-only --no-exec --no-semantic。无需启动 Runtime 即可查看完整命令目录：

    wcode help-all
    wcode help-all setup
    wcode help-all --json

## 发布验证

发布前审计会重放历史 Tunnel/Trust、TUI Authorization、WebUI Refresh/Error、真实 WebKit 布局和 Release Fail-Closed 反例。当前 Observatory 行为套件 44/44 通过，TUI Console 9/9 通过，真实 macOS WebKit 覆盖 12 个布局宽度，完整 Production Browser Audit 覆盖 96 个宽度/语言/主题/Tab 组合；Release Audit 报告同时绑定输入 Digest、Git HEAD 与 Clean/Dirty Worktree 状态。

可变工作树上的绿灯不能作为最终发布证据。真正的 Release Commit 必须通过完整 Locked Rust Gate、Clippy -D warnings、优化 Release Build、Design State、Release Contract、macOS WebKit、--require-clean 的 30 轮 Adversarial Audit，以及该精确 SHA 的普通 CI。

发布流程为：审查后的 Commit → 非强推 Push → 精确 SHA CI 全绿 → v0.8.0 Tag → 跨平台分发构建与 GitHub Release。
