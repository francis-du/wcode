# 架构与模块边界

wcode 把物理结构当作工程约束，而不是单纯代码风格。`convention_status` 会同时返回具体 finding 和 `architecture_guidance`，让 Agent 在文件或目录真正失控之前就知道什么时候应该拆。

## 默认拆分信号

| 信号 | 默认行为 |
| --- | --- |
| 维护源码达到 **600 行** | Warning：继续加行为前，检查是否应按责任拆文件或模块。 |
| 维护源码超过 **1,000 行** | Error：禁止继续增长，必须先分解；生成代码继续豁免。 |
| 同一目录包含 **24+ 个维护源码文件** | Warning：按共同 owner / 生命周期建立子模块或子目录，不继续堆平铺文件。 |
| Rust crate 根目录出现 **16+ 个非入口模块** | Warning：优先迁到 `src/<domain>/`；重复前缀会进一步提示形成真实模块边界。 |
| 某责任已经有稳定公开合同、独立测试且依赖单向 | 才考虑抽 crate 或独立仓库；不能只为了让架构图好看而拆。 |

这些阈值是要求检查责任归属，不是鼓励把代码切成大量碎片。一个合理边界通常至少分离了以下一项：协议、存储、UI、编排、领域逻辑、生命周期、权威、安全/部署信任或可独立测试的合同。

## 应该拆到哪一层

**拆文件**：一个维护文件开始承担多个独立责任，或者接近 600 行预警线。

**拆模块/目录**：多个文件拥有共同领域 owner、命名前缀、生命周期或测试边界时，建立 `src/<domain>/`，不要长期在 crate 根目录堆前缀文件。

**抽 crate**：只有依赖可以保持单向、合同可以独立测试，而且不会复制规范状态时才做。跨领域不可变事实适合抽取；强状态编排通常不适合为了形式硬拆。

**拆仓库**：源码访问、许可证、发布节奏、部署权威或信任边界明显不同。拆仓后仍必须保持单向依赖，不能让公开产品反过来依赖私有源码。

当前商业化拆分就是这个规则：公开 `wcode` 继续拥有 Apache-2.0 产品与规范工程事实；独立商业仓只单向消费公开合同。

## Agent 执行规范

向已有 Warning 的文件或高密度目录继续增加行为之前，Agent 应先查看 `convention_status` 和 Product Scope。优先搬出已经存在的完整责任，而不是为了拆而新增无意义抽象。若移动改变了 owner 或公开合同，需要同步 Design State，并执行 architecture / standalone 门禁。

Warning 本身不授权大重构；除非任务明确改变兼容合同，否则应保留公开路径和状态兼容。相反，`oversized-source-module` 是硬错误：模块没有降到上限以内之前，不允许继续增长。
