# wcode v0.3.0

v0.3.0 turns wcode's existing control-plane primitives into one Product Scope-aware Software Intelligence Runtime and tightens the path from desired state to safe implementation, verification evidence and reconciliation.

## Product Scopes

wcode now has one canonical Product Scope registry covering `runtime`, `integrations`, `workspace`, `design`, `graph`, `semantics`, `traceability`, `risk`, `verification`, `evidence`, `reconciliation`, and `experience`.

The registry is not decorative metadata. It drives:

- source architecture and Convention classification;
- scoped `software_context` navigation;
- scoped semantic queries while retaining freeform business scopes;
- `project_context` capability discovery;
- MCP Tool `_meta` through `dev.wcode/productScopes`;
- MCP resource discovery through `wcode://runtime/product-scopes`;
- repository-level `scope_status` auditing with per-scope counts and bounded unmapped source paths;
- agent/skill workflow guidance;
- Design State components and acceptance chains.

## Workspace and Scheduler

- Workspace coding primitives remain workspace-rooted, hash-guarded and atomic.
- Destructive actions use exact dynamic authorization and one-shot grants where required.
- Model-requested bare executable names can become per-Workspace `CommandAccess` requests; operators can select and approve/deny pending requests from either the TUI or protected Project Observatory. Shell interpreters and path-bearing program names remain hard-blocked.
- `parallel_tools` is backed by a reusable resource Scheduler rather than a read-only fan-out special case.
- Scheduler resources model reads, writes, creates, move sources, move destinations and deletes.
- Independent work fans out; conflicting resources are dependency ordered. The adaptive default capacity is now CPU×12, clamped to 96–192, while the explicit Harness maximum remains 256.
- Same-file `apply_edits` may coalesce only on the same observed SHA with non-overlapping, unambiguous edits.
- Interactive coding writes retain same-directory atomic replacement and SHA/path safety but no longer force data+directory fsync on every small edit; `project_context` parallelizes its Convention and Language Quality scans, exact search streams directory traversal into parallel workers, bounded reads avoid whole-file line-vector allocation, multi-edit line bounds share one line index, and request/response byte metrics count JSON through a streaming writer instead of allocating a second serialized buffer.

## Software Intelligence

- Design State, Actual State, syntax/semantic graph facts, semantic registry, traceability, drift, impact and risk are connected through the Harness.
- Software context can be narrowed by Product Scope before broad source reads.
- Semantic scopes are persistent and behavioral: requested scopes filter scoped facts, while unscoped facts remain global.
- Semantic providers remain explicit about precision and all indexed languages retain an honest provider/fallback path.
- The new Language Quality Matrix treats support as a vector across syntax, semantics, format, lint, type/static analysis, tests, security and advanced verification stages; repository-declared/native tools outrank imposed defaults and missing dimensions remain visible gaps.
- `language_quality_run` executes only detected, repository-declared, available, check-only providers through the trusted authorization boundary and records current-revision Evidence without formatter/fixer write mode.
- Composite graph history/query/diff preserves provider/precision/revision provenance.

## Project Observatory

- The protected `/intelligence` WebUI is requirement-first and organized around wcode's control loop: **Desired State → Actual State → Change → Proof → Convergence**, instead of rendering the generic Software Graph as a primary ball/node canvas.
- A Requirement Board exposes each feature's intent, component responsibilities/dependencies, current implementation symbols/files, Acceptance/Verification, constraints and ADRs, and assigns an explicit `stable`, `changing`, `needs_convergence`, or `incomplete` convergence state with bounded blockers.
- Proof is revision-exact: the current view counts only Evidence whose code and Design revisions match the live repository, so historical failures or passes are not presented as current proof.
- The runtime regenerates a bounded current Software Graph for observability and compares declared component dependencies with code-derived Calls/Imports/References/Runtime relationships, preserving provider/precision instead of claiming compiler certainty. A code change that removes a declared dependency automatically changes the owning Requirement from `stable` to `needs_convergence`.
- Repository and per-feature statistics include source files/lines/bytes, implementation lines, symbols/call edges, language and Product-Scope distributions, plus current Git additions/deletions and mapped affected requirements.
- Meaningful deduplicated Software Graph snapshots remain the architecture history source; the UI shows revision time, latest Node/Edge `+ / - / ~` deltas, and attributable changed source paths.
- A Language Quality Matrix panel shows detected-language capability coverage and gaps in the same operator surface.

## Verification and Evidence

- Risk-adaptive Verification Mesh combines bounded deterministic checks, independent review, Property/Mutation/Fuzz/Runtime-Canary stage evidence and human approval where required.
- Structural maintainability is now a first-class approval gate: `review_changes` emits deterministic 1k-boundary/concentrated-growth/cross-Product-Scope signals, medium-and-higher risk plans include a blind `maintainability_review` job with a shared code-judo/canonical-boundary rubric, and correctness evidence cannot substitute for that review.
- Stage aggregation remains fail-closed by producer; one producer's failure cannot be hidden by another producer's pass.
- Evidence remains persistent, workspace-scoped and provenance-bearing.
- Reconciliation execution is durable and dependency-aware; Verification and HumanApproval remain system evidence gates rather than model-claimable work.

## MCP, agents and connectors

- Modern and supported compatibility MCP revisions continue through one shared runtime.
- MCP exposes Tools, Prompts, Resources and durable owner-scoped Tasks.
- OAuth/connector support retains PKCE, protected-resource metadata, resource binding, bounded Dynamic Client Registration metadata and safe web/native redirect profiles.
- Origin validation remains explicit for the HTTP MCP surface.
- Local stdio and portable coding-agent skill export remain supported.
- The portable Skill follows the agentic-engineering model: short always-on map, progressive disclosure, isolated workers for independent work, deterministic policy gates, and revision-exact Evidence; model consensus never substitutes for proof.
- Agents can discover Product Scopes via Tool metadata or the Product Scope MCP resource.

## Convention and architecture governance

- Convention policies cover all 22 indexed languages without inventing one universal naming style.
- Convention status reports file naming, architecture domains, Product Scope mappings, unmapped/unclassified source, flat Rust growth and oversized modules.
- Source code is organized around wcode Product Scopes instead of the former flat/technical-layer growth pattern.
- Large Runtime/Workspace/Intelligence/MCP/Experience responsibilities were split into bounded modules without changing external crate/module contracts; the Ratatui monitor now separates lifecycle/main layout from detailed Setup/activity/Intelligence/help/footer rendering.

## Design State

- `design_init` now keeps Desired State sparse and meaningful: initialization creates only `.wcode/project.yaml` and `design/product.yaml`; requirement/component/constraint/acceptance/decision collections remain absent until real design content exists instead of being materialized as empty `[]` placeholders.
- Runtime Evidence, Verification, Graph, Semantic, Reconciliation and MCP Task state continues to live in wcode's user-level state directory rather than polluting repository `.wcode/`.

The working tree expands Design State across the implemented Product Scope capabilities and maps them to real implementation symbols and acceptance tests. The current design contains 28 Requirements, 27 Components, 28 Acceptance Criteria and 24 Constraints; `design_status` is valid and traceability resolves Requirement → Component, Design → Implementation and Acceptance → Verification at 100% in the working tree. The release gate must re-check those facts for the tagged revision. Future-only placeholder components are not treated as implemented capabilities.

## Upgrade

Build/install v0.3.0 using the repository install scripts or release artifacts for your platform. `.wcode/` Design State remains in the repository. Evidence, Verification state, semantic facts, graph/provider history, Reconciliation state, and MCP Task snapshots remain in wcode's user-level state directory keyed by the canonical workspace root; they do not modify the repository. Validate a working tree with `design_status`, `traceability_status`, `review_changes`, and `verify_project` after upgrading.

## Release gates

A v0.3.0 release is publishable only after the repository passes the locked full gate: formatting, type checking, tests, Clippy with warnings denied, and optimized release build, with valid Design State and resolvable traceability. The quality workflow now runs `wcode intelligence --check --json` against the repository so Design, all three traceability dimensions, the explicitly declared canonical Product Scope source mapping, and required Convention policies are enforced rather than documented only. Product Scope mapping is only fail-closed for Design States that opt into `CONSTRAINT-PRODUCT-SCOPE-CANONICAL`, so third-party workspaces are not forced into wcode's own source layout. Do not infer a successful release from this document alone; use the actual CI/release evidence for the tagged revision.
